# Summary

Two-dimensional correlation spectroscopy (2DCOS) [@noda1993] takes a series of
spectra measured under some perturbation, such as temperature, concentration,
or time, and produces two correlation maps. The synchronous map shows which
bands change together across the series. The asynchronous map separates
overlapped bands and gives the order in which they respond. The method is
routinely applied where a single spectrum is too congested to interpret, for
instance in hydrogen-bonded liquids [@noda2000generalized].

`crosspeak` is a Python implementation of generalized 2DCOS. It computes the
synchronous and asynchronous correlation intensities via the Hilbert-Noda
transform [@noda2000hilbert], supports heterospectral correlation between
distinct spectral regions, moving-window analysis, and autopeak detection, and
includes the preprocessing that 2DCOS results are sensitive to: smoothing,
region selection, and several normalisation schemes. Plotting functions produce
the standard paired synchronous and asynchronous contour presentation.

# Statement of need

The 2DCOS literature rests on software that is difficult to inspect or rerun.
The most widely used tool, `2Dshige`, is closed-source Windows freeware that has
not been updated since its 2005 release; as Lasch and Noda observe, it "cannot
be adapted or modified by others" [@lasch2019]. The one peer-reviewed
open-source implementation, `corr2D` [@geitner2019], is written in R. Python has
no equivalent: the reference script distributed alongside @morita2020 has no
releases, tests, or packaging, and the correlation code that exists in general
chemometrics libraries is partial and unmaintained. A correlation map published
today usually cannot be regenerated by anyone but its author.

`crosspeak` addresses this gap for the Python ecosystem. It is pip-installable,
unit-tested, and its numerical core is checked against `corr2D` on a shared
input, so agreement between two independent implementations in two languages can
be verified rather than assumed. The central object is an immutable
`SpectralSeries`; every preprocessing function returns a new series rather than
modifying its input, so the pipeline behind any given map is explicit in the
code that produced it. This is not a stylistic preference. Normalisation choice
changes the apparent magnitude of cross-peaks while leaving their pattern
intact, and two maps prepared under different normalisations are not comparable.
An inspectable pipeline is the practical defence.

I wrote `crosspeak` during a study of water uptake in choline chloride deep
eutectic solvents, where establishing the sequence of hydrogen-bond disruption
required heterospectral correlation between the O-H stretch and the H-O-H bend
across a water-content series.

# Conventions

Implementations of 2DCOS differ in ways that change the numbers without either
being wrong, so `crosspeak` states its choices. The dynamic spectrum is formed
by mean-centring across the perturbation axis. The synchronous intensity is
normalised by 1/(m-1) for m perturbation points. The Hilbert-Noda matrix is
defined as N_jk = 1/(pi(k-j)) off the diagonal and zero on it; the opposite sign
convention negates the entire asynchronous map and inverts every conclusion
about sequential order. Input arrays carry the perturbation along rows and the
spectral variable along columns, following @noda2000generalized. Even sampling
of the perturbation variable is assumed [@noda2003].

# Functionality

- `SpectralSeries`: immutable container for a perturbation-ordered series
- `synchronous`, `asynchronous`: correlation intensities after @noda2000hilbert
- `synchronous_hetero`, `asynchronous_hetero`: correlation between two regions
- `find_autopeaks`: peak detection on the synchronous diagonal
- Preprocessing: Savitzky-Golay smoothing, region cropping, mean-centring,
  and area, vector (L2), and SNV normalisation
- Plotting: contour maps and paired synchronous/asynchronous panels
- I/O: CSV readers and cubic-spline regridding to a common wavenumber grid

# Quality control

Unit tests cover the numerical core. Some assert algebraic identities that hold
for any correct implementation: the synchronous matrix is symmetric, the
asynchronous matrix is antisymmetric with a zero diagonal, and heterospectral
correlation of a series with itself reproduces the homospectral result.

The rest check the code against `corr2D` [@geitner2019] on a shared simulated
dataset, which is a stronger test because the two compute the same quantity by
different routes: a direct Hilbert-Noda matrix product here, a fast Fourier
transform there. The two do not use the same normalisation. `corr2D` scales by
1/(pi(m-1)), and its transform carries a further factor of m, so its synchronous
matrix equals m/pi times the one defined above; the reference fixtures are
rescaled accordingly and then agree to floating-point tolerance (rtol = 1e-10).
The asynchronous matrices are not related by any scalar, since the Hilbert-Noda
matrix is a truncated convolution kernel while the Fourier route gives the exact
discrete Hilbert transform; the two differ in magnitude at every series length
without converging, but agree in sign everywhere, and the sequential-order rules
depend only on sign. A regression test guards this relationship so that a change
to the transform cannot pass unnoticed. Continuous integration runs the test
suite and linter on every push.
